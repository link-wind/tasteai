先建立能验证的 baseline

每轮全量扫描，M 轮、初始 N 个单位的粗略上界为 O(MN)，另有候选排序与对象分配开销。

优化前先固定语料、边界、并列规则与基准实现。

正确性约束：同一输入与规则约定 → 相同 merge 序列、词表字节与编码结果
测量维度：总耗时、峰值内存、扫描/更新次数、I/O 时间、并行合并开销

逐轮核对 pair、频次和新 ID；相同最终长度不代表相同规则。

预分词与频次聚合，先减少重复工作

重复片段可保存为“IDs + 权重”，相邻对频次乘权重，无需重复存储相同列表。

Python 的整数、列表和字典有对象开销；原始文件大小不等于处理时内存大小。

from collections import Counter
chunks = ["low", "low", "lower", "low"]
frequencies = Counter(chunks)
# {"low": 3, "lower": 1}，后续每条只保留一份 ID 序列

分片读取还需控制唯一片段、索引与中间结果的积累；必要时分区或落盘。

并行预分词：边界与可重复性比进程数更重要

按完整记录分派预分词任务，避免任意字节切片破坏 UTF-8 或正则边界。

固定清洗和预分词设置后归并频次。小任务过多时，序列化与进程开销可能抵消收益。

合并后只更新受影响的记录

维护 pair → 记录集合 倒排索引。只改写受影响记录：先扣旧计数，再合并，再加新计数与更新索引。

pair → 含有该 pair 的记录编号集合
对每个受影响记录：
  扣旧计数、移除旧索引 → 合并序列 → 加新计数、加入新索引

本课仍扫描受影响的整条记录。更细的邻接边维护与优先队列可继续减少工作，但实现更复杂。

affected = sorted(index[selected_pair])
for row_id in affected:

局部更新最容易错在哪里？

aaa 有重叠匹配；扣减计数时必须遵守非重叠替换，避免重复扣除。

索引集合只记录受影响记录；实际次数仍由记录内直方图乘权重计算。

交互实验

练习

自测与解析 · 6 题

先作答，再展开解析。

01 · 为什么不能只比较最终 token 数判断优化正确？

展开逐步解析

不同合并规则可能压缩到相同长度，却给新文本不同切分。应逐轮比对 pair、频次、新 ID 及最终字节词表，再做编码往返检查。

02 · 索引用 set 保存记录编号，为什么仍需相邻对计数器？

展开逐步解析

set 只去重受影响记录，一条记录里可能有多个同类相邻位置。频次必须按实际出现次数乘记录权重，不能用集合大小直接替代。

03 · 局部更新的 pair_checks 从 43 增到 52，算优化失败吗？

展开逐步解析

不能单凭一项判断。它减少其他记录访问，却增加受影响记录的旧/新检查并引入索引开销；是否更快或更省内存需要测实际目标指标。

04 · 把文件任意切成等长字节块，直接交给各 worker 有何风险？

展开逐步解析

可能切断 UTF-8 多字节字符，也可能切断正则片段，改变训练边界。应按完整文档/记录分派，或实现正确的边界恢复与去重。

05 · 堆中 pair 的计数已经下降，旧堆项为什么危险？

展开逐步解析

堆不会自动感知外部计数变化。若不检查版本或当前计数，过期项可能仍以旧高频值弹出，导致规则轨迹错误。

06 · 流式读文件是否足以保证内存有上限？

展开逐步解析

不够。若唯一片段表、反向索引和候选结构持续增长，常驻内存仍可能超限。需要同时约束读取缓冲和累积状态。
